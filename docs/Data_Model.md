**Module A: Clinical Writing**
**Version 1.0 — September 2026**
*Status: Approved for prototype build. PostgreSQL schema for Phase 2 backend.*

---

## 0. Document Purpose & Conventions

This document defines the full relational data model for Aurora Module A. It covers:

- Every table with field names, types, constraints, and defaults
- Relationships between tables with cardinality
- Index strategy per table
- Enum types
- Design notes explaining non-obvious decisions

**Conventions:**

| Convention | Meaning |
|-----------|---------|
| `PK` | Primary key |
| `FK` | Foreign key |
| `NN` | NOT NULL |
| `UQ` | Unique constraint |
| `IDX` | Index (non-unique) |
| `→` | References (FK target) |
| `[]` | Array type (PostgreSQL) |
| `JSONB` | Flexible JSON column (PostgreSQL) |
| `snake_case` | All table and column names |

**ID strategy:** All primary keys use `UUID` (generated by the application, not the database). This ensures IDs are safe to expose in URLs, are portable across environments, and do not leak sequence information.

**Enum naming convention — TypeScript vs SQL:** TypeScript uses kebab-case enum values (`'in-authoring'`, `'cross-functional-review'`). PostgreSQL uses snake_case (`'in_authoring'`, `'cross_functional_review'`). This conversion is handled by the API layer — never by frontend components or SQL queries directly. The conversion utility lives in `utils/enumConvert.ts`:

```typescript
export const toSQLEnum   = (value: string): string => value.replace(/-/g, '_')
export const fromSQLEnum = (value: string): string => value.replace(/_/g, '-')
// toSQLEnum('in-authoring')            → 'in_authoring'
// toSQLEnum('cross-functional-review') → 'cross_functional_review'
// fromSQLEnum('crm_in_progress')       → 'crm-in-progress'
```

Frontend components always use kebab-case. SQL queries always use snake_case. Prisma handles this automatically in Phase 2 via `@map` decorators.

**Timestamps:** All `created_at`, `updated_at` fields store UTC timestamps as `TIMESTAMPTZ`. Application is responsible for sending UTC; display conversion is a frontend concern.

**Soft deletes:** No tables use hard deletes. All records have a `deleted_at TIMESTAMPTZ NULL` column. Deleted records are excluded from application queries by default but retained for audit purposes. Three tables are intentional exceptions:
- `audit_entries` — never deleted, not even soft-deleted. Immutable by design (FR-A-060).
- `signature_records` — never deleted. Each record is a Part 11-compliant signed artefact (FR-A-066).
- `document_versions` — never deleted. Versions are immutable records; once created they exist permanently. Section-level restore (FR-A-029b) creates new versions, never overwrites old ones.

## 3. Platform Layer Tables

These tables are shared across all modules. They live in the `platform` schema.

### 3.1 `users`

```sql
CREATE TABLE users (
  id              UUID          PRIMARY KEY,
  email           TEXT          NOT NULL UNIQUE,           -- UQ
  name            TEXT          NOT NULL,
  initials        TEXT          NOT NULL,                  -- 2–3 chars, uppercase
  role_title      TEXT          NOT NULL,                  -- display role, e.g. "Lead Clinical Writer"
  colour_key      TEXT          NOT NULL,                  -- e.g. "MW" — maps to USER_COLOURS
  mfa_enabled     BOOLEAN       NOT NULL DEFAULT true,
  mfa_secret      TEXT,                                    -- TOTP secret, encrypted at rest
  last_login_at   TIMESTAMPTZ,
  created_at      TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
  deleted_at      TIMESTAMPTZ
);

-- Indexes
CREATE UNIQUE INDEX users_email_idx ON users (email) WHERE deleted_at IS NULL;
```

**Notes:**
- `colour_key` is a short string (e.g. "MW") that maps to the `USER_COLOURS` constant in the frontend. Stored here so the backend can generate avatar HTML without knowing the full colour table.
- `mfa_secret` is encrypted at rest using AES-256. Never returned in API responses.

### 3.2 `projects`

```sql
CREATE TABLE projects (
  id                  UUID            PRIMARY KEY,
  name                TEXT            NOT NULL,
  short_title         TEXT            NOT NULL,            -- e.g. "VELORA-301"
  client              TEXT            NOT NULL,
  therapeutic_area    TEXT            NOT NULL,
  phase               TEXT,                                -- "III", "II/III", etc.
  status              project_status  NOT NULL DEFAULT 'initiated',
  start_date          DATE            NOT NULL,
  data_cutoff_date    DATE,
  active_modules      TEXT[]          NOT NULL DEFAULT '{}', -- e.g. ['clinical_writing']
  submission_countries TEXT[]         NOT NULL DEFAULT '{}', -- e.g. ['US', 'EU', 'JP'] — drives §16.4 requirement (FR-A-003)
  created_by          UUID            NOT NULL REFERENCES users(id),
  created_at          TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
  updated_at          TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
  deleted_at          TIMESTAMPTZ,

  -- Closed is hard: once closed, status cannot change
  CONSTRAINT closed_is_terminal
    CHECK (deleted_at IS NULL OR status != 'closed')
);

-- Indexes
CREATE INDEX projects_status_idx ON projects (status) WHERE deleted_at IS NULL;
CREATE INDEX projects_ta_idx     ON projects (therapeutic_area) WHERE deleted_at IS NULL;
```

**Notes:**
- `active_modules` is a text array — when Module B is added to a project, `'scientific_writing'` is appended.
- The `closed_is_terminal` check is enforced at the DB level as a belt-and-suspenders measure. Application layer also enforces this.

## 4. Module A — Document Tables

### 4.1 `documents`

```sql
CREATE TABLE documents (
  id              UUID            PRIMARY KEY,
  project_id      UUID            NOT NULL REFERENCES projects(id),
  type            document_type   NOT NULL,
  title           TEXT            NOT NULL,
  status          document_status NOT NULL DEFAULT 'not_started',
  stage           document_stage  NOT NULL DEFAULT 'study_start_up',
  therapeutic_area TEXT           NOT NULL,                -- inherited from project, immutable
  template_id     UUID,                                    -- FK to document_templates (future)
  assignee_id     UUID            NOT NULL REFERENCES users(id),
  current_version_id UUID,                                 -- FK to document_versions (set after first save)
  target_completion_date DATE,
  submitted_for_review_at TIMESTAMPTZ,
  signed_at       TIMESTAMPTZ,
  watermarked     BOOLEAN         NOT NULL DEFAULT true,   -- removed on final sign-off only
  created_by      UUID            NOT NULL REFERENCES users(id),
  created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
  deleted_at      TIMESTAMPTZ
);

-- Indexes
CREATE INDEX documents_project_idx  ON documents (project_id) WHERE deleted_at IS NULL;
CREATE INDEX documents_status_idx   ON documents (status)     WHERE deleted_at IS NULL;
CREATE INDEX documents_stage_idx    ON documents (stage)      WHERE deleted_at IS NULL;
CREATE INDEX documents_assignee_idx ON documents (assignee_id) WHERE deleted_at IS NULL;
```

**Notes:**
- `therapeutic_area` is copied from the project at document creation and is immutable thereafter (per FR-A-002).
- `current_version_id` is a forward reference to `document_versions`. Set after the first save. Circular FK is resolved by deferring the constraint.
- `watermarked = false` is set only when the final signature chain is completed.

---

### 4.2 `document_versions`

```sql
CREATE TABLE document_versions (
  id              UUID        PRIMARY KEY,
  document_id     UUID        NOT NULL REFERENCES documents(id),
  version_number  TEXT        NOT NULL,                    -- "v0.1", "v0.2", etc.
  label           TEXT        NOT NULL,                    -- "Draft", "For Review", "Final"
  content_hash    TEXT        NOT NULL,                    -- SHA-256 of full document content
  is_current      BOOLEAN     NOT NULL DEFAULT true,
  created_by      UUID        NOT NULL REFERENCES users(id),
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  restore_source  JSONB,                                   -- null if normal save; {fromVersionId, sections[], reason} if restored

  UNIQUE (document_id, version_number)
);

-- Indexes
CREATE INDEX doc_versions_document_idx ON document_versions (document_id);
CREATE INDEX doc_versions_current_idx  ON document_versions (document_id, is_current) WHERE is_current = true;
```

**Notes:**
- Only one version per document has `is_current = true`. When a new version is saved, the previous version's `is_current` is set to `false` atomically in the same transaction.
- `restore_source` records the provenance of restored versions (FR-A-029b). Immutable once set.
- `content_hash` is used by the e-signature chain to bind the signature to the exact document state (FR-A-066).

**Notes:**

- `content_html` stores the editor's HTML output. For Phase 2, consider moving large content to object storage and storing only a reference here.

### 4.4 `provenance_records`

```sql
CREATE TABLE provenance_records (
  id                  UUID        PRIMARY KEY,
  document_version_id UUID        NOT NULL REFERENCES document_versions(id),
  section_id          TEXT        NOT NULL,
  span_id             TEXT        NOT NULL,                -- unique span identifier within section
  span_text           TEXT        NOT NULL,                -- the actual text span
  source_type         TEXT        NOT NULL,                -- 'ai_draft' | 'human' | 'restored'
  source_ref          TEXT,                                -- TLF table ref, SAP section, etc.
  ai_model            TEXT,                                -- 'claude-sonnet' etc. — null if human
  ai_generated_at     TIMESTAMPTZ,
  accepted_by         UUID        REFERENCES users(id),
  accepted_at         TIMESTAMPTZ,
  created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()

  -- Provenance records are NEVER updated or deleted
);

-- Indexes
CREATE INDEX provenance_version_idx ON provenance_records (document_version_id);
CREATE INDEX provenance_section_idx ON provenance_records (document_version_id, section_id);
CREATE INDEX provenance_span_idx    ON provenance_records (span_id);
```

**Notes:**
- Immutable table. No UPDATE or DELETE ever touches this table. Application enforces; DB trigger can enforce in Phase 2.
- Every AI-drafted text span that a human accepts creates a row here. This is the Part 11 AI provenance record (FR-A-021).

## 8. Audit Trail Tables

### 8.1 `audit_entries`

```sql
CREATE TABLE audit_entries (
  id              UUID                PRIMARY KEY,
  entity_type     TEXT                NOT NULL,            -- 'document'|'comment'|'checklist_item'|'signature'|etc.
  entity_id       TEXT                NOT NULL,            -- UUID or "CMT-###" depending on entity_type
  event_type      audit_event_type    NOT NULL,
  actor_id        UUID                NOT NULL REFERENCES users(id),
  actor_name      TEXT                NOT NULL,            -- denormalised — preserved even if user deleted
  actor_role      TEXT                NOT NULL,            -- denormalised
  detail          TEXT                NOT NULL,            -- human-readable description
  old_value       JSONB,                                   -- null for creates
  new_value       JSONB,                                   -- null for deletes
  session_id      TEXT                NOT NULL,            -- authenticated session identifier
  timestamp_utc   TIMESTAMPTZ         NOT NULL,            -- server-set, not client-provided
  time_source     TEXT                NOT NULL DEFAULT 'server', -- 'server'|'ntp-stratum-2' (Phase 2)
  ip_address      INET,
  device_info     TEXT

  -- CRITICAL: NO PRIMARY KEY UPDATE, NO DELETE EVER — enforced by DB trigger in Phase 2
);

-- Indexes
CREATE INDEX audit_entity_idx    ON audit_entries (entity_type, entity_id);
CREATE INDEX audit_actor_idx     ON audit_entries (actor_id);
CREATE INDEX audit_timestamp_idx ON audit_entries (timestamp_utc DESC);
CREATE INDEX audit_event_idx     ON audit_entries (event_type);
```

**Notes:**
- `timestamp_utc` is always set by the server, never trusted from the client.
- `actor_name` and `actor_role` are denormalised — if a user's name changes or they are deleted, their historical audit entries must remain accurate.
- This table is the most critical in the entire system. In Phase 2, a DB trigger enforces no UPDATE or DELETE.
- In Phase 1 (prototype), audit entries are simulated from `data/auditTrail.json`. The mock MSW handler appends to an in-memory array.

```sql
  signer_role         TEXT                NOT NULL,        -- denormalised
  step                INTEGER             NOT NULL,        -- 1, 2, 3, 4
  meaning             signature_meaning   NOT NULL,
  status              signature_status    NOT NULL DEFAULT 'queued',
  scope_sections      TEXT[],                              -- null = whole document
  document_hash       TEXT,                                -- SHA-256 at time of signing
  version_at_signing  TEXT,                                -- "v0.4"
  credential_hash     TEXT,                                -- hashed credential (never plaintext)
  timestamp_utc       TIMESTAMPTZ,                         -- set on signing
  local_time          TEXT,                                -- "16:32 CET" — signer's local time
  time_source         TEXT,                                -- "Aurora time server, NTP stratum 2"
  auth_method         TEXT,                                -- "password re-auth + TOTP"
  device_info         TEXT,
  network_info        TEXT,
  audit_entry_id      UUID                REFERENCES audit_entries(id),

  -- Signed records are immutable
  UNIQUE (chain_id, step)
);

-- Indexes
CREATE INDEX sig_records_chain_idx  ON signature_records (chain_id);
CREATE INDEX sig_records_signer_idx ON signature_records (signer_id);
```

**Notes:**
- `id` format "SIG-####-##" (e.g. "SIG-0417-JO") is human-readable and surfaced in the UI and certificate downloads.
- `signer_name` and `signer_role` are denormalised — the signature record must be self-contained.
- Once `status = 'signed'`, no fields may be updated. Application enforces; DB trigger in Phase 2.

## 13. MedDRA Lookup Table (Phase 2)

MedDRA is a licensed subscription database from MSSO. In Phase 1, it is represented as a static JSON file (`data/meddra.json`) containing a mock subset of terms relevant to the VELORA-301 prototype. In Phase 2, the full MedDRA hierarchy is loaded from the MSSO subscription feed and stored in a read-only lookup table.

```sql
CREATE TABLE meddra_terms (
  id              UUID        PRIMARY KEY,
  version         TEXT        NOT NULL,                    -- "27.0", "27.1"
  pt_code         TEXT        NOT NULL,                    -- Preferred Term code, e.g. "10035742"
  pt_name         TEXT        NOT NULL,                    -- Preferred Term name, e.g. "Pneumonitis"
  llt_code        TEXT,                                    -- Lowest Level Term code
  llt_name        TEXT,                                    -- Lowest Level Term name
  hlt_code        TEXT,                                    -- High Level Term code
  hlt_name        TEXT,                                    -- High Level Term name
  hlgt_code       TEXT,                                    -- High Level Group Term code
  hlgt_name       TEXT,                                    -- High Level Group Term name
  soc_code        TEXT        NOT NULL,                    -- System Organ Class code
  soc_name        TEXT        NOT NULL,                    -- e.g. "Respiratory, thoracic and mediastinal disorders"
  is_current      BOOLEAN     NOT NULL DEFAULT true,       -- false for retired terms

  UNIQUE (version, pt_code)
);

CREATE INDEX meddra_pt_name_idx  ON meddra_terms (pt_name, version) WHERE is_current = true;
CREATE INDEX meddra_pt_code_idx  ON meddra_terms (pt_code, version) WHERE is_current = true;
CREATE INDEX meddra_soc_idx      ON meddra_terms (soc_code, version) WHERE is_current = true;
```

```sql
-- Track which MedDRA terms are used in each document
CREATE TABLE document_meddra_usage (
  id              UUID        PRIMARY KEY,
  document_id     UUID        NOT NULL REFERENCES documents(id),
  section_ref     TEXT        NOT NULL,
  pt_code         TEXT        NOT NULL,
  pt_name         TEXT        NOT NULL,
  meddra_version  TEXT        NOT NULL,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  UNIQUE (document_id, section_ref, pt_code)
);

CREATE INDEX meddra_usage_document_idx ON document_meddra_usage (document_id);
```

**Notes:**
- This table is read-only from the application's perspective — only updated via the MSSO subscription refresh process (Admin-triggered).
- `document_meddra_usage` tracks which terms are actively used per document/section, enabling the "✓ Used in document" indicator in the MedDRA lookup panel (Screen 26).
- FR-A-032: while procurement is pending, the mock interface (`data/meddra.json`) stands in. The swap to the real table requires only removing the MSW handler — no component changes.

## 15. Phase 2 Migration Strategy

When the real backend is scaffolded:

1. Run `prisma init` and define the Prisma schema from this document
2. Run `prisma generate` — Prisma generates TypeScript types that match `packages/types/src/domain.ts` exactly (validate they match before proceeding)
3. Run `prisma migrate dev --name init` to create all tables
4. Seed from the Phase 1 JSON files: `prisma db seed`
5. Replace MSW handlers one endpoint at a time, starting with read-only endpoints (`GET /documents`, `GET /documents/:id`) before write endpoints
6. The circular FK between `documents.current_version_id` and `document_versions.document_id` requires `prisma migrate` to use `defer` or a two-step migration — document this in the migration notes
