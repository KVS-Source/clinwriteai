# ADR 0002: ORM — Prisma for app-level data, raw SQL for the audit trail

**Status**: Accepted (2026-10-05, after adversarial review)
**Date**: 2026-10-05
**Owner**: Tech lead
**Deciders**: Tech lead, 2× BE engineers
**Supersedes**: —
**Superseded by**: —

## Context

`docs/demo/01-architecture.md §1` and `02-datamodel.md` imply "Prisma + PostgreSQL" without a formal decision. The data model is 154 tables with wide variety:

- 90% of tables are conventional: foreign keys, indexes, enum columns, moderate JSON use.
- The **audit trail** (`audit_events`) requires hash-chained rows, partial indexes, `UPDATE`/`DELETE` grants revoked at the DB level, and append-only semantics. Prisma's schema language does not express partial indexes or row-level grants cleanly.
- The **Claims Matrix similarity engine** (ADR 0012) needs `pgvector` with cosine-similarity indexes. Prisma `pgvector` support is community-driven and lags upstream.

Need to decide: Prisma for everything? Drizzle (closer to SQL, more flexible) for everything? Or a hybrid?

## Decision

**Prisma 5.x for 95% of the data model**, with **raw SQL + Postgres migrations for the audit trail table and `pgvector` indexes**.

**Two commitments baked into the decision** (added after adversarial review):

1. **Multi-file Prisma schema from day one.** Use the `prismaSchemaFolder` preview feature so the 154-table schema is split per module (`prisma/schema/platform.prisma`, `prisma/schema/clinical.prisma`, etc.) rather than growing one monolithic file. Prisma struggles with large single-file schemas at this scale.
2. **Checkpoint at Phase 1 Week 4.** After the Platform layer (~20 tables) is modelled, the team explicitly re-evaluates: is Prisma still carrying its weight, or should we flip to Drizzle before the module backends start? Flipping is cheap at Week 4 and expensive at Week 20.

The hybrid is managed by having `prisma/migrations/` be the sole migration source of truth; raw-SQL migrations are placed in Prisma migration folders as `.sql` files alongside Prisma's own. The audit trail is modelled in Prisma as a read-only type (so services can query it) but writes go through a hand-written repository that executes a prepared `INSERT` directly.

**Alternative seriously considered but not chosen**: Typed SQL (pgtyped, Zapatos) instead of an ORM. See new "Option E" below. The decider was ship-speed on a 9-month timeline vs long-term technical purity.

## Options considered

### Option A — Prisma everywhere
- **Pros**: Single toolchain, familiar to most Node BE engineers, excellent TypeScript inference, mature migration tooling.
- **Cons**: Cannot cleanly express partial indexes (`WHERE deleted_at IS NULL`), row-level grants, materialised views, or `pgvector` operators. Would force us into escape hatches (`$queryRaw`, Prisma migration `--create-only` + hand-edit) in exactly the places where correctness matters most.
- **Rough effort / cost**: Zero for happy path; ongoing friction and workarounds for the audit trail + vector columns.

### Option B — Drizzle everywhere
- **Pros**: Closer to SQL, first-class support for Postgres-specific features (partial indexes, generated columns, custom types, `pgvector`), schema is TypeScript so partial indexes compose naturally.
- **Cons**: Newer, smaller community. The 95% of our model that is conventional does not benefit from Drizzle's advantages, and we lose Prisma Studio (handy for ops). Fewer BE engineers have Drizzle on their CVs — hiring friction.
- **Rough effort / cost**: Steeper learning curve across the team; ongoing lower hiring pool.

### Option C — Prisma + raw SQL for the hard parts *(chosen)*
- **Pros**: Keeps the happy-path 95% in Prisma (where it shines). Isolates the 5% that needs SQL power into a documented, bounded escape hatch. Doesn't require the whole team to learn two ORMs.
- **Cons**: Two mental models for two slices of the schema; the audit trail repository is hand-written and must be covered by extra integration tests.
- **Rough effort / cost**: ~1 engineer-week to set up the raw-SQL migration convention and the audit repository scaffold.

### Option D — Drizzle for `audit_events` + `pgvector`, Prisma for the rest
- **Pros**: Each ORM where it's strongest.
- **Cons**: Two migration pipelines that have to be kept in sync — operational nightmare. Rejected.

### Option E — Typed SQL (pgtyped / Zapatos / Kanel) + raw SQL for audit/pgvector
*(Added after adversarial review — the "why do we need an ORM at all?" question.)*
- **Pros**
  - Write real SQL in `.sql` files; a codegen tool introspects Postgres and generates TS types per query. No ORM between you and the DB; full SQL power; type-safe results.
  - No type drift (types are generated from the actual schema at build time).
  - No ORM-specific query inefficiencies or escape hatches.
  - Smaller dependency surface than Prisma; no 5MB generated client.
  - Scales cleanly to 154 tables because there is no single schema file to grow.
- **Cons**
  - Codegen step in CI; one more thing to run.
  - More boilerplate than Prisma (every CRUD query hand-written), less than pure raw SQL.
  - Migration tooling is DIY (Flyway / node-pg-migrate / Sqitch — all mature, all separate).
  - Smaller communities than Prisma; fewer Stack Overflow answers.
  - Requires at least one engineer who prefers SQL-first and will enforce idioms across the team.
- **Rough effort / cost**: ~2–3 engineer-weeks to set up tooling + migration pipeline + initial typed-query conventions. Ongoing hand-rolled queries are slower per-table than Prisma but faster than pure raw SQL.
- **Why rejected despite being technically clean**: On the 9-month-to-GA timeline with a 4–6 person team of mixed backgrounds, the Prisma boilerplate win is worth more than typed SQL's purity. If the hiring pool skews heavily toward SQL-first engineers (e.g. ex-DBA, ex-Go, ex-Rust), revisit at the Phase 1 Week 4 checkpoint.

### Option F — Pure raw SQL + hand-maintained types
- **Pros**: Zero abstraction, maximum control.
- **Cons** (fatal at 154 tables × 4–6 engineers × 9 months): type drift between DB and code is inevitable; inconsistent query patterns across engineers accumulate into unmaintainable code; ~11,500 lines of CRUD boilerplate to write and maintain.
- **Rejected.**

## Rationale

Decisive factor: **the audit trail and pgvector are the places where the schema's correctness matters most, and both are where Prisma is weakest**. Trying to force Prisma on them creates fragile code; letting them live in raw SQL (inside Prisma's migration folder) keeps a single migration pipeline while giving us the Postgres power we need.

Hiring is a quiet second consideration: Prisma is on more CVs than Drizzle in 2026, and the audit trail is the one place where senior-engineer attention is warranted anyway.

## Consequences

### Positive
- Day-to-day development uses Prisma's excellent TypeScript inference.
- `audit_events` is correctly modelled: append-only, hash-chained, partial indexes, DB-level grants revoked.
- `pgvector` columns use native operators (`<=>`, `<->`) without ORM gymnastics.
- Single migration pipeline (`prisma/migrations/`).

### Negative
- Engineers must remember: audit trail = raw SQL, everything else = Prisma. Mitigated by locating the audit repository in a single file with a clear comment at the top of the schema.
- Prisma schema file does not reflect the audit table's full constraints — the SQL migration is the source of truth. Address with a `// SEE: prisma/migrations/XXXX_audit_trail.sql` comment on the Prisma model.

### Neutral / downstream work
- Phase 1 Week 3 scaffolds `apps/api/prisma/schema/` (multi-file, per-module layout) + the raw-SQL migration convention.
- Phase 1 Week 4 implements the `audit_events` table + repository with 100% integration test coverage.
- **Phase 1 Week 4 ORM checkpoint**: team retrospective on Prisma's fit at ~20 tables. Decision gate: continue (default) or flip to Drizzle / typed SQL before module backends start. Document the decision as an amendment to this ADR.
- A linter rule should block direct `prisma.auditEvent.*` writes from handler code — writes must go through the repository.

## Compliance implications

- **21 CFR Part 11 §11.10(e)**: Audit trail must be computer-generated, time-stamped, and secure. Hash-chaining + DB-level revoked grants is the mechanism. Prisma's inability to express this is precisely why we're using raw SQL for this table.
- **GAMP 5**: The audit repository and its SQL migration are both Design Specification (DS) artefacts in Phase 5.
