# Scheduled deploy — runbook

How the ClinWrite platform auto-deploys itself on the VPS, and the
cheat sheet for operators.

## What it does

Every 15 minutes, Mon-Fri, 09:00-19:00 IST, a systemd timer fires
`/opt/platform/scripts/auto-deploy.sh`:

1. Takes a `flock` so overlapping ticks never collide.
2. `git fetch`es; if `origin/main` matches local HEAD → logs "nothing
   to deploy" and exits (zero cost, no rebuild).
3. If there's new work → runs
   `/opt/platform/repo/infra/standalone/scripts/deploy.sh` (the same
   script a human would run manually).
4. On non-zero exit → sends an email with the last 100 lines of the
   deploy log to all addresses in `RECIPIENTS=` in auto-deploy.sh
   (defaults to chetan@, prajakta@, dev@genbioca.com).
5. Every run writes a full log to
   `/var/log/platform/deploy-<UTC>.log`. Logs older than 30 days are
   pruned automatically.

## Files

| Path (VPS) | Source (repo) | Role |
|------------|---------------|------|
| `/opt/platform/scripts/auto-deploy.sh` | `infra/standalone/scripts/auto-deploy.sh` | The wrapper |
| `/etc/systemd/system/platform-deploy.service` | `infra/standalone/systemd/platform-deploy.service` | Oneshot that runs the wrapper |
| `/etc/systemd/system/platform-deploy.timer` | `infra/standalone/systemd/platform-deploy.timer` | Fires the service on schedule |
| `/opt/platform/env/api.env` | generated by `first-run-bootstrap.sh` | Carries NOTIFICATION_SMTP_* vars |

Both unit files + the wrapper are installed by `first-run-bootstrap.sh`.
Re-running bootstrap is safe (idempotent).

## Email alerts

Uses SMTP via Python's `smtplib`, reading `NOTIFICATION_SMTP_*` keys
from `/opt/platform/env/api.env`. This is the same mechanism the
genrac-scheduled-deploy on this VPS uses — bootstrap doesn't populate
these keys automatically; copy from an existing project with:

```bash
sudo bash -c '
  grep -vE "^NOTIFICATION_(SMTP_|FROM_)" /opt/platform/env/api.env > /tmp/api.env.new
  grep -E "^NOTIFICATION_(SMTP_|FROM_)" /var/www/genrac/apps/api/.env >> /tmp/api.env.new
  install -o platform -g platform -m 600 /tmp/api.env.new /opt/platform/env/api.env
  rm /tmp/api.env.new
'
```

If NOTIFICATION_SMTP_* vars are missing, the schedule still runs — the
failure path just logs "Email FAILED: …" instead of actually sending.

## Cheat sheet

```bash
# When's the next scheduled deploy?
sudo systemctl list-timers platform-deploy.timer

# Fire a deploy manually right now (uses the schedule's exact script)
sudo systemctl start platform-deploy.service

# Watch the last run's log live
sudo tail -f "$(sudo ls -t /var/log/platform/deploy-*.log | head -1)"

# See the last few runs
sudo ls -lt /var/log/platform/deploy-*.log | head -5

# Service status + last journal lines
sudo systemctl status platform-deploy.service --no-pager -l
sudo journalctl -u platform-deploy.service --since '24 hours ago' --no-pager

# Pause the schedule (vacation / maintenance)
sudo systemctl stop platform-deploy.timer
# Resume
sudo systemctl start platform-deploy.timer
# Permanently disable (survives reboot)
sudo systemctl disable --now platform-deploy.timer

# Change recipients — edit the RECIPIENTS=... line
sudo nano /opt/platform/scripts/auto-deploy.sh

# Change schedule — edit OnCalendar= lines, then
sudo systemctl daemon-reload
sudo systemctl restart platform-deploy.timer

# Send a one-off test email through the exact SMTP path the failure
# alert uses (does NOT touch the deploy itself).
sudo bash -c '
  set -a
  source <(grep -E "^NOTIFICATION_(SMTP_|FROM_)" /opt/platform/env/api.env)
  set +a
  RECIPIENTS_ENV="chetan@genbioca.com" python3 <<PYEOF
import os, ssl, smtplib, socket
from email.message import EmailMessage
msg = EmailMessage()
msg["Subject"] = "[ClinWrite] alert pipeline probe"
msg["From"] = os.environ.get("NOTIFICATION_FROM_ADDRESS", os.environ["NOTIFICATION_SMTP_USER"])
msg["To"] = os.environ["RECIPIENTS_ENV"]
msg.set_content(f"Probe from {socket.gethostname()}. If you see this, the pipeline works.")
with smtplib.SMTP_SSL(os.environ["NOTIFICATION_SMTP_HOST"], int(os.environ["NOTIFICATION_SMTP_PORT"]), context=ssl.create_default_context(), timeout=30) as s:
    s.login(os.environ["NOTIFICATION_SMTP_USER"], os.environ["NOTIFICATION_SMTP_PASSWORD"])
    s.send_message(msg)
print("sent")
PYEOF
'
```

## Common operations

### A new engineer wants the deploy to notify them too

Edit `/opt/platform/scripts/auto-deploy.sh`, change the `RECIPIENTS=`
line (comma-separated), save. No restart needed — next failure uses the
new list.

To make the change survive a bootstrap re-run, also update the same
line in `infra/standalone/scripts/auto-deploy.sh` in the repo and
commit.

### Schedule needs to change (e.g. extend to Saturdays)

Edit `OnCalendar=` lines in
`/etc/systemd/system/platform-deploy.timer`. For "every 15 min
Mon-Sat 09:00-19:00 IST":

```ini
OnCalendar=Mon..Sat *-*-* 09..18:00/15 Asia/Kolkata
OnCalendar=Mon..Sat *-*-* 19:00:00 Asia/Kolkata
```

Then:

```bash
sudo systemctl daemon-reload
sudo systemctl restart platform-deploy.timer
sudo systemctl list-timers platform-deploy.timer  # verify NEXT
```

Also update `infra/standalone/systemd/platform-deploy.timer` in the
repo to keep bootstrap in sync.

### A deploy keeps failing — triage order

1. Open the most recent deploy log:
   `sudo tail -200 "$(sudo ls -t /var/log/platform/deploy-*.log | head -1)"`
2. The last error is usually npm (build break) or Prisma (migration).
3. For a persistent problem that's blocking the schedule, pause the
   timer (`sudo systemctl stop platform-deploy.timer`), fix on the
   `main` branch, then resume.

## Why systemd timer and not cron

- Already proven on this VPS (genrac uses it)
- `journalctl -u platform-deploy.service` gives free structured logs
  alongside the file logs
- `Persistent=true` catches missed runs after a reboot — cron doesn't
- `systemd-analyze verify` validates unit files before enabling —
  easier than crontab typo debugging
- `systemctl list-timers` shows next + last fire times at a glance
